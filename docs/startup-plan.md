# 一体化启动实施记录

目标：Windows 双击一个入口启动现有 QQ 消息监控系统，保留用户数据库和第三方组件。

用户已确认方案并要求开始修改，直接在原目录实施；修改前备份到 backups/startup-20261004-192501。

1. 添加 runtime_support.py：持久化会话密钥、单实例文件锁、识别后台健康状态。
2. 添加 windows_job.py 和 launcher.py：Tk 启动窗口；线程化 Web 服务；通过 Windows Job 管理自建 NapCat 进程树；复用已有连接；提供路径选择、日志、登录页入口和统一退出。
3. 修改数据库、后端和前端：迁移 auto_start 配置，受认证的自动启动接口，真实 OneBot 连接/在线状态，可靠停止和重连。
4. 更新启动批处理，新增首次初始化脚本及使用说明。
5. unittest 使用临时数据目录验证迁移、自动启动、身份验证、断线状态、单实例锁；集成验证端口冲突和进程树清理；不使用真实 QQ 账号发送消息。

边界：不自动安装或升级 QQ/NapCat，不改动第三方源文件；首次登录及失效后的扫码由用户完成。直接打开 app.py 仍受支持。

实施记录：核心功能已完成；8项初始回归测试从失败转为通过；随后加入 Windows Job、端口冲突、进程失败恢复、真实 HTTP/Tk 启停与批处理 CRLF 回归测试，共17项。入口冒烟测试使用中文及空格路径，发现并修复 LF 换行导致 cmd 跳过判断后卡住的问题；改用 CRLF 后通过。Python 与前端 JavaScript 语法检查通过。

独立代码审查发现并修复：普通端口占用误判为 NapCat；进程创建失败后的 Job/日志句柄未释放导致无法重试。增加服务身份探测、Job 活跃进程计数和失败释放逻辑。

决定：在原目录修改并保留原文件备份，避免工作树无法携带大型未跟踪 NapCat 目录。通过启动器本地监听，不改变直接运行 app.py/Docker 的原监听行为。真实 QQ 账号登录保留为用户侧验收。
